# Database foundation — Phase 2

- **IMPLEMENTED:** ordered migrations; PostGIS preflight; ownership constraints; geography columns; indexes; timestamp triggers; default-deny RLS; rollback-only catalog/integrity assertions; pinned CLI and clean-reset verification scripts/workflow.
- **DATABASE GATE:** CI runs against a fresh Supabase/PostgreSQL container. This checkout cannot run Docker or `psql`; local database behavior remains unverified until the GitHub Actions workflow succeeds. A TypeScript build is not a database result.

## Migration order

1. `20261004000000_enable_postgis.sql` — Phase 1 foundation; creates the `extensions` schema and requests PostGIS there.
2. `20261004010000_phase2_ownership_schema.sql` — checks that PostGIS is actually installed in `extensions` and that `pg_catalog.gen_random_uuid()` / geography `ST_DWithin` are available; creates organizations, workspaces, projects, datasets, project associations and the shared timestamp trigger.
3. `20261004020000_phase2_spatial_entities.sql` — creates the five spatial record tables, indexes, update triggers, RLS and client-role revocations.

The preflight intentionally fails if an earlier PostGIS installation is in another schema. `CREATE EXTENSION IF NOT EXISTS ... WITH SCHEMA extensions` does not move an extension already installed elsewhere. Do not work around that failure by relying on `search_path`; inspect the database and choose an explicit, reviewed migration strategy.

UUID primary keys use `pg_catalog.gen_random_uuid()`. PostgreSQL 13+ provides this in `pg_catalog`; the migration checks the exact function before creating tables. It does not add `pgcrypto` or depend on an extension that duplicates built-in functionality. `supabase/config.toml` targets PostgreSQL 17.

## Ownership model

```text
organizations
└── workspaces
    ├── projects
    │   └── project_datasets ─────┐
    ├── datasets ─────────────────┘  (many-to-many; same workspace enforced)
    │   ├── locations
    │   ├── customers
    │   ├── competitors
    │   └── branches
    └── analysis_locations (scoped to a project in the same workspace)
```

Projects and datasets are both workspace-owned but are not parented to one another. `project_datasets` is the reusable many-to-many association. A dataset can be linked to multiple projects, but not across workspaces.

The database enforces ownership, rather than trusting route code:

- `projects` and `datasets` each have `UNIQUE (id, workspace_id)` for composite FK targets.
- Each business table has `FOREIGN KEY (dataset_id, workspace_id) REFERENCES datasets (id, workspace_id)`.
- `project_datasets` has composite FKs to `(project_id, workspace_id)` and `(dataset_id, workspace_id)`.
- `analysis_locations` has a composite FK to `(project_id, workspace_id)`.

## Tables and deletion behavior

| Table | Responsibility | Delete behavior |
|---|---|---|
| `organizations` | Tenant root: name, globally unique canonical slug, object metadata and timestamps. | A referenced organization cannot be deleted. |
| `workspaces` | Organization-scoped workspace and slug. Slug uniqueness is `(organization_id, slug)`. | Workspace deletion is restricted while tenant data exists. |
| `projects` | Workspace-scoped project; status is only `active` or `archived`. | Analysis locations restrict project deletion. Association rows are removed with the project. |
| `datasets` | Reusable workspace-owned data collection; `dataset_type` is extensible text, not a closed enum. | Referenced business records restrict dataset deletion. Association rows are removed with the dataset. |
| `project_datasets` | Many-to-many link plus workspace ownership and `created_at`. | Cascades delete only the link row, never the project, dataset or business records. |
| `locations` | Generic mapped POIs/business locations with category, source and external ID. | Dataset deletion is restricted while records exist. |
| `customers` | Customer data including contact fields, exact point, orders and revenue. | Dataset deletion is restricted while records exist. Treat the row as sensitive. |
| `competitors` | Competitor and brand locations with normalized category fields. | Dataset deletion is restricted while records exist. |
| `branches` | Existing business branches and optional revenue/customer aggregates. | Dataset deletion is restricted while records exist. |
| `analysis_locations` | Persisted candidate locations, explicitly distinct from unsaved map-click state. | Project and workspace deletion are restricted while records exist. No score fields are frozen yet. |

Business tables use `created_at` and trigger-maintained `updated_at` (`timestamptz`). `project_datasets` has only `created_at`, since the relationship itself has no mutable business state. A single `public.set_updated_at()` trigger function serves mutable tables.

Deletion is conservative: organization/workspace/project/dataset business data is not silently cascaded away. The only cascading action is removal of `project_datasets` association rows when a linked project or dataset is deleted; datasets remain reusable and their business rows remain protected by `ON DELETE RESTRICT`.

## Geospatial choice: `geography(Point, 4326)`

Every authoritative point column is `extensions.geography(Point, 4326)`. This is intentional because accurate meter-based local distance queries are central to the product:

- `ST_DWithin(geography, geography, distance_meters)` uses meter distances and the spheroid by default; it can use a GiST index on the geography column.
- Geography GiST also supports nearest-neighbor candidate ordering. The `<->` KNN ordering is spherical; refine/reorder shortlisted results with `ST_Distance(geography, geography, true)` when spheroidal ranking is required.
- No separately authoritative latitude/longitude columns are stored. Geography enforces the point/SRID type; database checks validate non-empty stored points and their coordinate bounds. PostGIS normalizes longitude during geometry-to-geography conversion, so raw input longitude bounds must be validated before casting; the runtime domain validator does so. The rollback-only SQL gate asserts this observed normalization and verifies that an out-of-range latitude is rejected.
- GeoJSON serialization should explicitly cast to geometry, e.g. `extensions.st_asgeojson(spatial_point::extensions.geometry)`. GeoJSON coordinate order is longitude, latitude.
- Future point-in-polygon work can cast the WGS84 point to geometry and compare it with a WGS84 polygon using `ST_Covers`/`ST_Intersects`. The polygon remains a geometry because polygon topology/overlay operations are geometry-first. Service areas and metric analytics still need server-side design.

A schematic radius predicate is:

```sql
SELECT id, category
FROM public.locations
WHERE workspace_id = $1
  AND dataset_id = $2
  AND extensions.st_dwithin(
        spatial_point,
        extensions.st_setsrid(extensions.st_makepoint($3, $4), 4326)::extensions.geography,
        $5 -- meters
      );
```

Parameters `$3`, `$4` are longitude then latitude; `$5` is meters. This is a query pattern only, not an implemented API or radius-analysis feature.

## Constraints and indexes

Spatial point columns are non-null, typed `geography(Point,4326)`, non-empty and checked for coordinate bounds. Text slugs are canonical lowercase URL slugs; required names/categories are non-empty. Dataset types remain extensible; project status is constrained to the requested two values. JSONB metadata must be an object. Customer revenue and branch revenue are `numeric(18,2)`, never floating point; counts are non-negative integers.

Each spatial GiST index accelerates spatial candidate filtering/distance queries on its corresponding table:

- `locations_spatial_gix`
- `customers_spatial_gix`
- `competitors_spatial_gix`
- `branches_spatial_gix`
- `analysis_locations_spatial_gix`

Selected B-tree indexes match anticipated access paths: list projects/datasets by workspace; filter points by `(workspace_id, dataset_id, category/segment)`; list analysis locations by `(workspace_id, project_id, created_at)`; and join project/dataset associations in either direction or check workspace ownership. Partial unique indexes on `(dataset_id, external_id)` support source-row upserts without preventing multiple null external IDs. No indexes are added for every individual field. Validate actual query plans with `EXPLAIN (ANALYZE, BUFFERS)` once representative data and queries exist.

## RLS and grants

**Implemented now:** RLS is enabled on all ten tenant-owned tables. There are deliberately **no policies**. Table privileges are revoked from `PUBLIC`, `anon`, and `authenticated`, so client roles have no access while membership/authentication rules are absent. No `USING (true)` or other development policy exists.

**Required before client access:** authentication work must define workspace membership and role-aware policies, and it must explicitly restore the minimum necessary SQL `GRANT` privileges. The Phase 2 `REVOKE` remains effective even if an RLS policy is later added; a policy alone does not grant table privileges. A future `workspace_members` table may link `workspace_id` and `user_id`, with a role and uniqueness on `(workspace_id, user_id)`, but it is not created here. Service-role credentials remain server-only; RLS does not make a service-role key safe for a browser.

## PII and domain boundaries

The SQL `customers` row contains sensitive name, phone, address and revenue fields. `src/lib/domain/map-location.ts` defines a separate validated/display-level selection model. `src/lib/map/map-feature-adapter.ts` serializes only the allow-listed `id`, `kind`, `category` and validated Point coordinates; it never serializes name, address, phone or revenue. IDs must be database UUIDs or known synthetic fixture/candidate IDs, not source contact identifiers. Tests deliberately pass private extra fields and a phone-like ID and confirm they cannot enter map output. This DTO omits `name` for all entity types; Phase 3/4 may define a separate normal business/POI DTO with an explicitly approved display name, while keeping customer map DTOs strongly PII-limited.

`src/lib/database/row-types.ts` contains explicit read-only TypeScript mirrors of the SQL columns, separate from the validated domain types and GeoJSON DTOs. They are **manual, not generated or verified against a live Supabase instance**. Raw geography is intentionally typed `unknown`, and numeric values retain a string-or-number transport boundary; a future data-access mapper must parse them before use. The SQL migrations remain canonical. After applying/verifying the schema locally, generate Supabase `Database` types and reconcile the module; keep row types server-side and map only validated, display-safe DTOs into MapLibre.

## Verification

`supabase/tests/phase2_integrity.sql` is a rollback-only live-database assertion script, run with `psql` and `ON_ERROR_STOP`. It requires PostgreSQL 17 and PostGIS >=3.3.0, prints the actual PostgreSQL/extension/library versions, checks that PostGIS is installed in `extensions`, and verifies the expected schema-qualified function signatures. It inspects system catalogs for all ten tables, five `geography(Point,4326)` typmods, and valid GiST definitions that index `spatial_point`.

The same transaction verifies zero policies, RLS enabled on all tenant tables, no table ACL privileges for `PUBLIC`, `anon` or `authenticated`, both directions of cross-workspace `project_datasets` rejection, dataset-owned business-row FK rejection, cross-workspace `analysis_locations` rejection, valid same-workspace inserts, trigger advancement, and conservative delete/cascade behavior. A Tashkent pair sanity test checks finite positive geography distance in a safe meter range and verifies `ST_DWithin` just below/above the measured spheroidal distance. All synthetic rows are rolled back.

The GitHub Actions workflow and local script both perform a clean reset before these assertions. CI also compares the generated types to the committed generated file and runs the application pipeline. Local Docker/`psql` are unavailable in this workspace, so no local migration or SQL-test result is claimed. See [setup.md](setup.md) for commands and workflow details.
