## Migration order

1. `20261004000000_enable_postgis.sql` — Phase 1 foundation; creates the `extensions` schema and requests PostGIS there.
2. `20261004010000_phase2_ownership_schema.sql` — checks that PostGIS is actually installed in `extensions` and that `pg_catalog.gen_random_uuid()` / geography `ST_DWithin` are available; creates organizations, workspaces, projects, datasets, project associations and the shared timestamp trigger.
3. `20261004020000_phase2_spatial_entities.sql` — creates the five spatial record tables, indexes, update triggers, RLS and client-role revocations.
4. `20261004030000_phase3_demo_spatial_queries.sql` — creates the two `SECURITY INVOKER` demo spatial RPCs, grants `SELECT` on the demo read tables to `service_role`, revokes `EXECUTE` from `PUBLIC`/`anon`/`authenticated`, and documents each function.

`supabase/seed.sql` is **not** a migration. It is deterministic synthetic demo data loaded by `supabase db reset --local` (configured under `[db.seed]` in `supabase/config.toml`) and by CI. Production deployments apply migrations only and never seed this file.

The preflight intentionally fails if an earlier PostGIS installation is in another schema. `CREATE EXTENSION IF NOT EXISTS ... WITH SCHEMA extensions` does not move an extension already installed elsewhere. Do not work around that failure by relying on `search_path`; inspect the database and choose an explicit, reviewed migration strategy.

UUID primary keys use `pg_catalog.gen_random_uuid()`. PostgreSQL 13+ provides this in `pg_catalog`; the migration checks the exact function before creating tables. It does not add `pgcrypto` or depend on an extension that duplicates built-in functionality. `supabase/config.toml` targets PostgreSQL 17.

## Ownership model

```text
organizations
└── workspaces
    ├── projects
    │   └── project_datasets ─────┐
    ├── datasets ─────────────────┘  (many-to-many; same workspace enforced)
    │   ├── locations
    │   ├── customers
    │   ├── competitors
    │   └── branches
    └── analysis_locations (scoped to a project in the same workspace)
```

Projects and datasets are both workspace-owned but are not parented to one another. `project_datasets` is the reusable many-to-many association. A dataset can be linked to multiple projects, but not across workspaces.

The database enforces ownership, rather than trusting route code:

- `projects` and `datasets` each have `UNIQUE (id, workspace_id)` for composite FK targets.
- Each business table has `FOREIGN KEY (dataset_id, workspace_id) REFERENCES datasets (id, workspace_id)`.
- `project_datasets` has composite FKs to `(project_id, workspace_id)` and `(dataset_id, workspace_id)`.
- `analysis_locations` has a composite FK to `(project_id, workspace_id)`.

## Tables and deletion behavior

| Table | Responsibility | Delete behavior |
|---|---|---|
| `organizations` | Tenant root: name, globally unique canonical slug, object metadata and timestamps. | A referenced organization cannot be deleted. |
| `workspaces` | Organization-scoped workspace and slug. Slug uniqueness is `(organization_id, slug)`. | Workspace deletion is restricted while tenant data exists. |
| `projects` | Workspace-scoped project; status is only `active` or `archived`. | Analysis locations restrict project deletion. Association rows are removed with the project. |
| `datasets` | Reusable workspace-owned data collection; `dataset_type` is extensible text, not a closed enum. | Referenced business records restrict dataset deletion. Association rows are removed with the dataset. |
| `project_datasets` | Many-to-many link plus workspace ownership and `created_at`. | Cascades delete only the link row, never the project, dataset or business records. |
| `locations` | Generic mapped POIs/business locations with category, source and external ID. | Dataset deletion is restricted while records exist. |
| `customers` | Customer data including contact fields, exact point, orders and revenue. | Dataset deletion is restricted while records exist. Treat the row as sensitive. |
| `competitors` | Competitor and brand locations with normalized category fields. | Dataset deletion is restricted while records exist. |
| `branches` | Existing business branches and optional revenue/customer aggregates. | Dataset deletion is restricted while records exist. |
| `analysis_locations` | Persisted candidate locations, explicitly distinct from unsaved map-click state. | Project and workspace deletion are restricted while records exist. No score fields are frozen yet. |

Business tables use `created_at` and trigger-maintained `updated_at` (`timestamptz`). `project_datasets` has only `created_at`, since the relationship itself has no mutable business state. A single `public.set_updated_at()` trigger function serves mutable tables.

Deletion is conservative: organization/workspace/project/dataset business data is not silently cascaded away. The only cascading action is removal of `project_datasets` association rows when a linked project or dataset is deleted; datasets remain reusable and their business rows remain protected by `ON DELETE RESTRICT`.

## Geospatial choice: `geography(Point, 4326)`

Every authoritative point column is `extensions.geography(Point, 4326)`. This is intentional because accurate meter-based local distance queries are central to the product:

- `ST_DWithin(geography, geography, distance_meters)` uses meter distances and the spheroid by default; it can use a GiST index on the geography column.
- Geography GiST also supports nearest-neighbor candidate ordering. The `<->` KNN ordering is spherical; refine/reorder shortlisted results with `ST_Distance(geography, geography, true)` when spheroidal ranking is required.
- No separately authoritative latitude/longitude columns are stored. Geography enforces the point/SRID type; database checks validate non-empty stored points and their coordinate bounds. PostGIS normalizes out-of-range coordinates during geometry-to-geography conversion, so raw longitude/latitude bounds must be validated before casting; the runtime domain validator does so. The rollback-only SQL gate asserts canonical stored coordinates, and application tests verify raw out-of-range coordinate rejection.
- GeoJSON serialization should explicitly cast to geometry, e.g. `extensions.st_asgeojson(spatial_point::extensions.geometry)`. GeoJSON coordinate order is longitude, latitude.
- Future point-in-polygon work can cast the WGS84 point to geometry and compare it with a WGS84 polygon using `ST_Covers`/`ST_Intersects`. The polygon remains a geometry because polygon topology/overlay operations are geometry-first. Service areas and metric analytics still need server-side design.

A schematic radius predicate is:

```sql
SELECT id, category
FROM public.locations
WHERE workspace_id = $1
  AND dataset_id = $2
  AND extensions.st_dwithin(
        spatial_point,
        extensions.st_setsrid(extensions.st_makepoint($3, $4), 4326)::extensions.geography,
        $5 -- meters
      );
```

Parameters `$3`, `$4` are longitude then latitude; `$5` is meters. This is a query pattern only, not an implemented API or radius-analysis feature.

## Phase 3 demo workspace and spatial RPCs

Live database access is restricted to one deterministic synthetic workspace:

| Object | Slug / id | Purpose |
|---|---|---|
| Organization | `atlas-demo` | Synthetic demo tenant root. |
| Workspace | `tashkent-demo` | The only workspace any Phase 3 API query may read. |
| Workspace | `isolation-test` | Synthetic isolation workspace used to prove no cross-workspace leakage. |
| Project | `Tashkent Retail Pilot` | Demo project and dataset associations. |
| Datasets | locations, competitors, branches, customers | Four demo datasets in `tashkent-demo`. |

`supabase/seed.sql` creates approximately 41 `locations`, 25 `competitors`, 9 `branches` and 241 `customers` in `tashkent-demo`, all synthetic and clustered around Tashkent (69.2797, 41.3111). Every kind has at least one point exactly on the demo center so 500 m assertions are deterministic. Each dataset also has a center point. The `isolation-test` workspace places a location, competitor, branch and customer at the same center with `test_only` metadata; the SQL suite proves the demo RPCs never count or return them.

Customer seed rows intentionally contain **no** name, phone, company or address values (all `NULL`) and a synthetic `external_id`/segment. Customer `revenue` values remain `numeric(18,2)` and are aggregated in SQL only.

### `public.demo_viewport_features`

```sql
public.demo_viewport_features(
  p_west double precision, p_south double precision,
  p_east double precision, p_north double precision,
  p_kinds text[] DEFAULT NULL, p_limit integer DEFAULT 2501
) RETURNS TABLE (
  feature_id uuid, kind text, category text,
  display_name text, longitude double precision, latitude double precision
)
```

- Validates bounds (each coordinate in range, `west <= east`, `south <= north`, max 40° longitude span, max 20° latitude span, max 400 deg² area) and rejects unknown kind values with SQLSTATE `22023`.
- Binds itself to `atlas-demo`/`tashkent-demo`; the caller cannot pass a workspace.
- Uses `extensions.st_makeenvelope(..., 4326)::extensions.geography` and `extensions.st_intersects(spatial_point, envelope)` — the geography predicate is index-friendly.
- Selects only the display-safe projection. The customer branch of the union projects `NULL::text` for `display_name`, so no customer name can be returned even by accident.
- Orders deterministically and applies `LIMIT p_limit`; the API requests `cap + 1` rows so truncation is detected explicitly.

### `public.demo_radius_analysis`

```sql
public.demo_radius_analysis(
  p_longitude double precision, p_latitude double precision, p_radius_meters double precision
) RETURNS TABLE (
  customers_count bigint, customers_revenue_total text,
  competitors_count bigint, branches_count bigint, locations_count bigint,
  category_distribution jsonb,
  nearest_branch_id uuid, nearest_branch_name text,
  nearest_branch_distance_meters double precision
)
```

- Validates coordinates and requires `100 <= p_radius_meters <= 20000` (SQLSTATE `22023` otherwise), raising `P0002` when the demo workspace is missing so the API can return 404.
- Filters with `extensions.st_dwithin(spatial_point, candidate, p_radius_meters, true)` (`true` = spheroidal) and computes the nearest branch with `extensions.st_distance(spatial_point, candidate, true)`.
- Returns **aggregates only**: counts, `sum(customer.revenue)` cast to `text` for exact decimal transport, a JSONB category distribution, and the nearest branch id/name/distance. It never returns customer rows or per-customer revenue.
- `sum(customer.revenue)` is `COALESCE`d to `0` and cast to `text` so PostgreSQL `numeric` precision is preserved across PostgREST and JavaScript, where a 64-bit IEEE double would be unsafe for currency.

Both functions are `STABLE`, `SECURITY INVOKER`, `SET search_path = pg_catalog`, and use schema-qualified PostGIS functions. No `SECURITY DEFINER` function exists in this project.

## Constraints and indexes

Spatial point columns are non-null, typed `geography(Point,4326)`, non-empty and checked for coordinate bounds. Text slugs are canonical lowercase URL slugs; required names/categories are non-empty. Dataset types remain extensible; project status is constrained to the requested two values. JSONB metadata must be an object. Customer revenue and branch revenue are `numeric(18,2)`, never floating point; counts are non-negative integers.

Each spatial GiST index accelerates spatial candidate filtering/distance queries on its corresponding table:

- `locations_spatial_gix`
- `customers_spatial_gix`
- `competitors_spatial_gix`
- `branches_spatial_gix`
- `analysis_locations_spatial_gix`

Selected B-tree indexes match anticipated access paths: list projects/datasets by workspace; filter points by `(workspace_id, dataset_id, category/segment)`; list analysis locations by `(workspace_id, project_id, created_at)`; and join project/dataset associations in either direction or check workspace ownership. Partial unique indexes on `(dataset_id, external_id)` support source-row upserts without preventing multiple null external IDs. No indexes are added for every individual field. Validate actual query plans with `EXPLAIN (ANALYZE, BUFFERS)` once representative data and queries exist.

## RLS and grants

**Implemented now:** RLS is enabled on all ten tenant-owned tables. There are deliberately **no policies**. Table privileges are revoked from `PUBLIC`, `anon`, and `authenticated`, so client roles have no access while membership/authentication rules are absent. No `USING (true)` or other development policy exists.

**Phase 3 addition:** the elevated `service_role` receives `SELECT` on `organizations`, `workspaces`, `locations`, `customers`, `competitors` and `branches`, plus `EXECUTE` on the two demo RPCs. `service_role` bypasses RLS by design; it is used only inside `server-only` modules, and each RPC independently binds itself to the demo workspace. `anon`/`authenticated` receive no new privileges and no `EXECUTE` rights. A `SECURITY INVOKER` function does not elevate privileges, so these grants are the minimum required for the server path.

**Required before client access:** authentication work must define workspace membership and role-aware policies, and it must explicitly restore the minimum necessary SQL `GRANT` privileges. The Phase 2 `REVOKE` remains effective even if an RLS policy is later added; a policy alone does not grant table privileges. A future `workspace_members` table may link `workspace_id` and `user_id`, with a role and uniqueness on `(workspace_id, user_id)`, but it is not created here. Service-role credentials remain server-only; RLS does not make a service-role key safe for a browser.

## PII and domain boundaries

The SQL `customers` row contains sensitive name, phone, address and revenue fields. `src/lib/domain/map-location.ts` defines a separate validated/display-level selection model. `src/lib/map/map-feature-adapter.ts` serializes only the allow-listed `id`, `kind`, `category` and validated Point coordinates; it never serializes name, address, phone or revenue. IDs must be database UUIDs or known synthetic fixture/candidate IDs, not source contact identifiers. Tests deliberately pass private extra fields and a phone-like ID and confirm they cannot enter map output. Phase 3 now additionally defines `SafeMapFeature`: business/POI/competitor/branch features explicitly allow a `name` from the database, while `CustomerMapFeature` remains `id`/`kind`/`category` only. The SQL projection, the server DTO mapper and the client response parser each independently reject a customer feature that carries a display name, and radius analysis returns aggregates only. The map endpoint never exposes phone, company, address, per-customer revenue or raw rows.

`src/lib/database/database.types.ts` is the Supabase CLI output generated from the clean schema after the live migration/integrity gate. It is not hand-edited. `src/lib/database/row-types.ts` now contains aliases directly derived from those generated `Row` types; it no longer redeclares SQL scalar fields. The generator emits PostGIS `spatial_point` as `unknown` and PostgreSQL `numeric` as `number`; `RawGeographyValue` and `RawNumericValue` are derived aliases, not replacement row definitions. A future precision-sensitive data-access mapper must avoid treating generated JavaScript numbers as exact decimals (for example, select numeric text or use a decimal representation). Keep raw rows server-side and map them into separate validated domain types and display-safe DTOs. The generator does not infer SQL `CHECK` constraints as TypeScript literals or JSON object shapes, so any future domain mapping must preserve those guarantees explicitly. Customer map DTOs must remain strongly PII-limited; a separate normal business/POI DTO may explicitly allow display names after review.

## Verification

`supabase/tests/phase2_integrity.sql` is a rollback-only live-database assertion script, run with `psql` and `ON_ERROR_STOP`. It requires PostgreSQL 17 and PostGIS >=3.3.0, prints the actual PostgreSQL/extension/library versions, checks that PostGIS is installed in `extensions`, and verifies the expected schema-qualified function signatures. It inspects system catalogs for all ten tables, five `geography(Point,4326)` typmods, and valid GiST definitions that index `spatial_point`.

The same transaction verifies zero policies, RLS enabled on all tenant tables, no table ACL privileges for `PUBLIC`, `anon` or `authenticated`, both directions of cross-workspace `project_datasets` rejection, dataset-owned business-row FK rejection, cross-workspace `analysis_locations` rejection, valid same-workspace inserts, trigger advancement, and conservative delete/cascade behavior. A Tashkent pair sanity test checks finite positive geography distance in a safe meter range and verifies `ST_DWithin` just below/above the measured spheroidal distance. All synthetic rows are rolled back.

`supabase/tests/phase3_spatial_queries.sql` extends the same rollback-only gate for Phase 3. Against the seeded demo data it asserts:

- 500 m, 1 km, 3 km and 5 km aggregates are monotone and each includes every feature kind at the demo center;
- the 500 m customer count and exact revenue equal an independent spheroidal `ST_DWithin` computation;
- an empty radius (0, 0) returns zero counts, `'0'` revenue, `'[]'` categories and a `NULL` nearest branch;
- the category distribution totals exactly `locations_count + competitors_count`;
- the nearest branch id, name and spheroidal distance match an independently ordered query;
- viewport features are non-empty inside the Tashkent demo window, honour the `kinds` filter, return no `display_name` for customers, and are empty for a viewport with no demo points;
- **cross-workspace isolation:** the `isolation-test` rows colocated inside the radius are confirmed to exist, confirmed to be excluded from the demo result, and confirmed absent from viewport features;
- radius/bbox validation raises `22023`; both RPCs are `SECURITY INVOKER`; `anon`/`authenticated` have no `EXECUTE` while `service_role` does;
- predicate-only `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` probes (with `enable_seqscan` disabled for the probe only) confirm the GiST indexes on `customers_spatial_gix`, `competitors_spatial_gix`, `branches_spatial_gix` and `locations_spatial_gix` are usable by the `ST_DWithin` and `ST_Intersects` predicates used by the RPCs, and report the observed plan execution times.

The GitHub Actions workflow and local script both perform a clean reset (with the synthetic seed) before these assertions. CI also compares the generated types to the committed generated file and runs the application pipeline. Local Docker/`psql` are unavailable in this workspace, so no local migration or SQL-test result is claimed. See [setup.md](setup.md) for commands and workflow details.
